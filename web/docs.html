Setup guide & reference

Everything from flashing the ESP32 to driving away with a gate that opens itself.

Quick start

Three steps from unboxing to working garage opener.

1
Flash the firmware

Download GarageAAtoESP32-flash-tool.zip from the Releases page, extract it, and double-click flash.bat. The tool installs PlatformIO if needed, lets you pick your board, detects the COM port, asks for your password, compiles, and flashes.

2
Install the Android app

Get it from the Play Store, or download the APK from the Releases page and sideload it.

3
Pair and go

Open Garage Opener on your phone — it walks you through scanning for your ESP32 and entering your password. Then connect your phone to Android Auto and tap Open Garage.

Flash tool

The flash tool is included in the release ZIP for both Windows (flash.bat) and Linux (flash.sh). It handles everything automatically — no manual toolchain setup needed.

What the tool does

  1. Installs PlatformIO automatically if not already present (Windows: via winget; Linux: via pip)
  2. Presents a board picker — choose your ESP32 variant
  3. Auto-detects the COM port by USB VID/PID — no guessing
  4. Asks for your trigger mechanism (relay active-high / relay active-low / transistor)
  5. Prompts for optional advanced settings: sleep duration, pulse duration, BLE device name
  6. Asks for your password and a confirmation to catch typos
  7. Compiles with your settings baked in as compiler flags — config.h is never modified
  8. Flashes and shows a success QR code linking to the Play Store
ℹ️

Your password is injected via compiler flags and exists only in RAM during compilation. It is never written to a file on disk.

Manual flash (advanced)

If you prefer to build from source directly:

cd firmware
pio run -e esp32c3 --target upload

Pass your settings as build flags:

pio run -e esp32c3 --target upload \
  -e esp32c3 \
  "--build-flags=-DUSER_PIN=\"\\\"my-password\\\"\" -DTRIGGER_MODE=MODE_TRANSISTOR"

Android app

The easiest path. Open the Play Store on your Android phone, search for Garage Opener or use the link below.

Get on Google Play
ℹ️

Play Store installs work in Android Auto out of the box — no developer mode required.

Download the latest .apk from the Releases page. Transfer it to your phone and install it.

⚠️

To install via ADB instead of a file manager:

The -i com.android.vending flag makes the install appear as a Play Store install, which avoids the Unknown Sources requirement on some Android Auto versions.

.\gradlew.bat assembleDebug  # Windows

APK: app/build/outputs/apk/debug/app-debug.apk

For a release build, create android/keystore.properties with your keystore credentials and run assembleRelease.

First launch

On first open, the app walks you through a three-screen onboarding flow:

  1. Welcome — explains what the app does
  2. Set password — enter the same password you used when flashing the firmware. This is stored locally on the phone and is never sent over the air
  3. Pair device — the app starts a BLE scan with a radar visual. Make sure the ESP32 is powered on and within ~10 m. Tap the device that appears in the list to pair it

After pairing, the main screen shows the paired device name and a presence indicator dot. When the dot is green and reads In range, the opener is advertising and ready.

Trigger options

The firmware supports three ways to press the fob button. Pick the one that fits your situation. All three use the same app, same authentication, and same Android Auto UI.

Option Soldering Fob modified Best for
A — Relay module ⭐ Recommended Yes (2 wires to fob pads) Yes Most setups. Beginner-friendly, no biasing knowledge needed.
B — Relay + power-rail switching Minimal (copper tape only) No Rented fob that must be returned untouched. Fully reversible.
C — Transistor Yes (2 wires to fob pads) Yes Power-critical deployments. Lower draw than relay (~20 mA).

Wiring diagrams

Option A — Relay module (recommended)

Recommended relay: Songle SRD-03VDC-SL-C (3V coil) — works directly with the ESP32's 3.3V GPIO and power rail. No transistor driver needed. Most relay modules with an onboard driver are active-high (MODE_RELAY_HIGH); use MODE_RELAY for older opto-isolated modules that trigger on LOW.

ESP32 GPIO 26 ──▶ Relay IN ESP32 GND ──▶ Relay GND ESP32 3.3V ──▶ Relay VCC Fob pad A ──▶ Relay COM Fob pad B ──▶ Relay NO (Normally Open)

In firmware: TRIGGER_MODE=MODE_RELAY_HIGH, TRIGGER_PIN=26

Option B — Relay + power-rail switching (renter-friendly)

Same relay wiring to the ESP32 as Option A. Instead of connecting to the fob's button pads, the relay switches the fob's battery ground rail. A clip or foam wedge holds the button depressed permanently — the fob fires every time it gets power.

ESP32 GPIO 26 ──▶ Relay IN ESP32 GND ──▶ Relay GND ESP32 3.3V ──▶ Relay VCC Relay COM ──▶ CR2032 − (external, negative terminal) Relay NO ──▶ Fob battery − contact (copper tape disc in slot) CR2032 + ──▶ Fob battery + contact (copper tape disc in slot)

No soldering inside the fob. Remove the copper tape discs and the button clip to return the fob exactly as received.

In firmware: TRIGGER_MODE=MODE_RELAY_HIGH, TRIGGER_PIN=26

Option C — Transistor (advanced)

One NPN transistor (2N2222, BC547, 2N3904) + one 1 kΩ resistor. Lower power draw than a relay (~20 mA vs ~70 mA) but requires transistor biasing knowledge.

ESP32 GPIO 26 ──[1 kΩ]──▶ Base (B) Collector (C) ──▶ Fob button pad A ESP32 GND ──────────▶ Emitter (E) Emitter (E) ──▶ Fob button pad B

GPIO HIGH → transistor saturates → fob pads shorted → gate opens.

In firmware: TRIGGER_MODE=MODE_TRANSISTOR, TRIGGER_PIN=26

Power options

The ESP32 spends most of its time in deep sleep (~19 mAh/day total at the default 5 s sleep cycle).

OptionSetupBest for
Wall outlet + USB charger Any 5V ≥ 500mA USB charger Socket nearby at the garage. Zero maintenance.
Solar power bank Solar panel → battery pack → ESP32 USB No socket. Self-sustaining outdoors.
USB power bank 10,000 mAh always-on bank No socket. ~12 months per charge at ~19 mAh/day.
Car USB / 12V socket ESP32 + fob in the car, powered by the car In-car deployment. Charges when car is on.
18650 + TP4056 + solar DIY — most flexible capacity/charging Custom enclosures, precise capacity sizing.
⚠️

Avoid power banks that auto-shut off when current draw drops — the ESP32 in deep sleep draws very little current and will trigger the auto-off. Use an always-on bank (e.g., Anker A1263 or equivalent).

Deployment modes

In the car (recommended for single-user)

ESP32 and fob both ride in the car, powered off the car's USB or 12V socket. Everything is in the same vehicle so BLE range is never a concern. The auto-fire feature (opens when the app detects the ESP32 in range on the AA screen) is particularly effective here.

  • No outdoor enclosure needed
  • Unit charges whenever the car is on
  • Not suitable for multiple users (the fob travels with one car)

At the garage (for multi-user)

ESP32 lives near the gate, powered by wall outlet, power bank, or solar. The fob stays at the garage. Anyone you share the password with can open the same gate from their own phone.

  • Supports multiple users and vehicles
  • BLE range 10–30 m through walls — position the ESP32 near the entrance
  • Firmware optimised for this mode: deep sleep between BLE advertising windows

Phone UI

The phone app is the primary setup surface and a functional opener in its own right.

Presence indicator

A low-power BLE scan filtered to your paired device's MAC runs while the main screen is in the foreground. The dot shows In range (green) when the opener has been heard within the last 8 s, Out of range (grey) otherwise. With 2+ devices paired, every paired BLE device's address is scanned at once, not just the currently-selected one.

Multiple openers

You're not limited to one device — pair any mix of BLE ESP32s and webhooks. Existing single-device installs migrate automatically with no visible change.

Once 2+ devices are paired, the main screen replaces the plain open button's device address with a Selected opener dropdown: tap it to see every paired device with its transport icon (Bluetooth/Wi-Fi), a type subtitle, and live in-range coloring for BLE devices. Picking a device applies immediately across every trigger surface — manual tap, Android Auto, the Wear tile, the watch app, voice, and the Quick Settings tile.

If any of your paired devices has a geofence configured, the dropdown pre-selects whichever device's geofence you're currently standing in instead of leaving the last manual pick selected — walk out to the car or stand near a gate and the right opener is already chosen. If two geofences overlap, both are pre-selected together (shown as "Main Garage + Side Gate") and tapping Open fires both at once. Tapping a different device overrides this pick until you leave and return to the main screen, at which point geofence presence takes over again. Devices with no geofence configured are unaffected — they're never auto-selected, only ever chosen manually or reached via their own BLE-presence auto-fire.

Settings shows a device list (name, transport, live BLE presence dot) once 2+ devices are paired; tapping a device opens its own Device Detail screen with re-pair/change-password (BLE) or edit (webhook) actions, its own geofence auto-open section, and a remove action.

Open history

Tap the history row at the bottom of the main screen to open a full timeline of every open event — timestamp, trigger source (manual tap, Android Auto, geofence auto-open, voice), and result. Geofence entries expand to show which gate passed and any suppression reasons. Opening 2+ devices at once (via geofence pre-selection) shows as a single grouped entry with a per-device breakdown, rather than separate unrelated-looking rows. Entries are grouped by day with sticky date headers.

Settings

Open settings via the ⚙ button in the top right. From here you can:

  • View, add, or remove paired devices (Repair / Pair another device / Unpair) — see Multiple openers above
  • Connect to the ESP32's Wi-Fi log server — the 📶 button appears next to the device address when the firmware was flashed with the web log feature enabled
  • Change your password
  • Configure geofence auto-open per device (location, radius, warmup ring)
  • Switch the app language (8 supported)
  • Enable Demo mode (runs the full UI flow without a real ESP32)
  • Share the geofence diagnostic log (Settings → Diagnostics)

Android Auto

The AA screen is built on the Car App Library. With a single device paired it shows one button: Open Garage. Designed to be safe to operate while driving.

States on the car screen

Multiple openers

With 2+ devices paired, the car screen shows a list instead of a single button — name, transport badge, and live BLE presence per row. Tapping a row opens that device and updates the phone's selection.

If a geofence is currently entered, the list is replaced by a single one-tap Open button naming the resolved device(s) — same one-tap experience as a single-device install, no need to pick from the list while driving. The picker only appears when no geofence is currently entered.

Auto-fire

When the AA screen is active and the presence scan detects a paired device in range, the app fires the open command automatically — once per AA session, for whichever specific device came into range (the selection updates to match). This means the gate often starts opening before you've pulled up to it. With 2+ devices paired, this only fires for the currently selected/resolved device, not any paired device that happens to be nearby. AA being connected is also the strongest signal in the geofence gate chain — if you use geofence auto-open, the AA path always takes priority.

Testing without a car

Use the Android Auto Desktop Head Unit emulator. Install it via Android Studio: Tools → SDK Manager → SDK Tools → Android Auto Desktop Head Unit Emulator. Start the DHU server on your phone (Android Auto → Developer settings → Start head unit server), then launch the emulator on your PC.

Wear OS

If you have a paired Wear OS watch, the companion app lets you open the garage directly from your wrist. Install the phone app from the Play Store — the watch app is delivered automatically to any connected Wear OS device.

Watch app

The watch app shows a single circular button (the same idle / sending / opened / failed states as the phone). Tap it to send the open command. The phone handles the BLE round-trip; the result comes back to the watch over the Wear OS data layer.

Multiple openers

With 2+ devices paired, the watch app and swipe-in tile show a device picker (name, transport badge, live BLE presence) instead of a single button, synced from the phone's device list. Picking a device on the watch updates the phone's selection too.

If a geofence is currently entered, the watch shows a single one-tap Open button for the resolved device(s) instead of the picker — same behavior as Android Auto. Falls back to the picker otherwise.

Watch tile

Add the Garage Opener tile to your watch face: swipe left to the tile carousel → Edit tiles → add Garage Opener. Tapping the tile launches the watch app and fires the open command immediately, without having to navigate to the app first.

Phone-initiated open

When you open the garage from the phone (manual tap, geofence, Android Auto, or voice), the watch receives the result too — Opened / Failed appears on the watch display with haptic feedback if the watch app is running or starts up via a push notification.

ℹ️

The watch never communicates directly with the ESP32 — it always routes through the paired phone over the Wear OS data layer. The phone must be within Bluetooth or Wi-Fi range of the watch for the command to reach the ESP32.

Voice commands

Say "Open the garage" through the car microphone or the steering wheel mic button. Google routes the matched intent directly to the running AA service, which fires the BLE command immediately — no screen touch needed.

Voice commands work in all 8 supported languages: English, Spanish, French, German, Catalan, Finnish, Portuguese (Portugal), and Italian.

ℹ️

The voice trigger uses Google Assistant / Gemini's App Actions (OPEN_APP_FEATURE BII). The intent routing is cloud-based, but the actual open command is fully local BLE — no cloud dependency once the intent arrives.

Quick Settings tile

Add the app to your notification shade for one-swipe access: long-press the shade → Edit tiles → drag Garage Opener into the active area.

The tile subtitle shows the current state: Sending… → Opened / Failed, then clears after 2 seconds. You can open the garage without unlocking the phone or opening the app.

There's also a launcher long-press shortcut: long-press the app icon → Open garage — launches the app and triggers the opener immediately.

With a single device paired, the tile fires immediately with no extra check, same as before. With 2+ devices paired, the tile also resolves geofence presence: it fires the matching device(s) directly if a geofence is currently entered, or opens the app to the picker if it can't tell which device you mean.

Geofence auto-open

When enabled, the garage opens automatically as you approach — no tap needed. Set it up per device in Settings → (device) → Auto-open → Garage location: tap the map to place that device's pin, drag the radius slider (15–75 m), and enable the Auto-open on arrival toggle. With 2+ devices paired, each device has its own independent geofence — a device with no geofence configured is simply never auto-fired by presence in a zone; it stays reachable via the ordinary picker and its own BLE-presence auto-fire.

Two geofences are registered per device around its location:

  • Inner geofence — at your configured radius. This is the trigger zone.
  • Outer geofence — at your configured radius + warmup ring offset (default 400 m, adjustable 15–1000 m). This is the GPS warmup zone (shown as a dashed ring in the picker).

When you cross the inner boundary inbound, the app runs a gate chain to decide whether to fire. When you cross the outer boundary inbound, the app pre-warms GPS so speed data is ready by the time the inner geofence fires.

Gate chain

Gates are evaluated in order. The first one that passes fires the open. If all fail, the trigger is suppressed and the full reason is written to the log.

GateConditionNotes
1 — AA connected Android Auto is actively connected Strongest signal — binary OS fact, no GPS needed. Always fires.
2 — Trigger speed Speed from the geofence event ≥ 12 km/h Only available if GPS was already warm at the moment of crossing. The outer geofence warmup makes this reliable.
3 — Activity IN_VEHICLE or ON_BICYCLE with ≥ 50% confidence Cached from Google's Activity Recognition API (30 s updates). Android classifies motorbikes as ON_BICYCLE at low speed — both activity types are accepted.
4 — Last known speed Most recent location fix ≥ 12 km/h, within 10 min Useful if navigation was recently active. Falls back to this if Gates 2 and 3 both fail.
ℹ️

Why AA is the best gate. AA being connected is a binary OS-level fact — it's the authoritative signal that you're in a vehicle and driving. It also keeps the phone's location stack warm, so geofence ENTER fires within ~1–2 s of the actual boundary crossing instead of the 30 s–2 min worst-case under Doze.

⚠️

Why speed is unreliable without AA. Geofences can fire off cell/WiFi positioning, which produces lat/lng but no speed. Speed requires GPS, which must be actively running. If no app is keeping GPS warm, the geofence event arrives with speed = 0. This is the problem the outer geofence warmup solves.

GPS warmup

The outer geofence fires at the configured warmup ring offset before the inner one (default 250 m, adjustable 15–1000 m via the slider in the geofence picker). On ENTER, a short-lived foreground service starts requesting location updates at 5 s intervals. GPS needs at least two consecutive fixes (~10 s) to compute speed. At 30–50 km/h you cross the default 250 m offset in 18–30 s — enough lead time to produce a valid speed reading before the inner geofence fires.

When warmup is skipped

  • Android Auto is connected — GPS is already warm via the AA location stack
  • Activity is STILL, WALKING, or RUNNING — clearly not in a vehicle
  • Activity is UNKNOWN and no prior inner geofence EXIT was recorded — likely still at home (see exit flag below)

IN_VEHICLE or ON_BICYCLE always starts warmup regardless of any flag.

Exit flag

When the inner geofence EXIT fires, a wasOutsideOuterGeofence flag is saved. On the next outer ENTER, UNKNOWN activity only starts warmup if this flag is set — confirming you genuinely left and came back. This prevents spurious GPS drain when you're stationary at home and the OS fires a re-register ENTER with ambiguous activity.

If the OS drops the EXIT event (which Android can do under Doze), the flag stays false for that cycle. IN_VEHICLE/ON_BICYCLE still override it, and the next full EXIT+ENTER cycle resets correctly. The flag is an optimistic hint, not a hard gate.

Warmup stop conditions

The service stops on whichever comes first:

  1. Outer or inner geofence EXIT — you left the zone
  2. Inner gate pass — the open fired; warmup is no longer needed
  3. Early activity stop — after a 30 s grace period, if a GPS fix arrives while cached activity reads ON_FOOT, WALKING, or RUNNING at ≥ 75% confidence and that reading is < 30 s old, warmup stops itself. This only saves battery/GPS usage — it never fires the open; the inner geofence gate chain is still the only trigger. STILL is deliberately excluded: an idling car at a red light is indistinguishable from a parked one to the motion sensors, so only gait-based activities (which a car can't produce) are trusted here. Speed alone is also deliberately not used, since the outer radius can span multiple stop signs or red lights where speed legitimately drops to 0 mid-approach.
  4. 5-minute timeout — safety net for dropped EXIT events. If the app crashes, the location client dies with it — no battery leak.

Debounce

After a successful open, a 10-second debounce prevents re-triggering. The debounce is tracked independently per device, so two geofences entered close together — an outer gate and a garage door on the same property, for example — can't have one device's auto-open silently suppress the other's. The timestamp is shared between the geofence service and the AA car screen via encrypted storage — cross-process races are absorbed. Only confirmed successful opens write the timestamp; failed attempts do not block subsequent triggers.

Re-registration

Both geofences are re-registered automatically on boot, app update, cold start, and every ~15 minutes via WorkManager (covers OEM process killers). setInitialTrigger(0) ensures re-registration never fires a spurious ENTER if you're already inside the zone.

Logs & diagnostics

Every gate evaluation is written to the geofence log — speeds, activity types, gate results, and suppression reasons. Share it via Settings → Diagnostics → Share geofence log to inspect exactly what happened on each approach.

The log retains the last 1 000 lines and is exportable as plain text.

ℹ️

Look for lines tagged GeofenceReceiver. A suppressed trigger always ends with "all gates failed" and lists the speed, activity type, and confidence that were checked.

ESP32 web log server

When enabled during flashing, the ESP32 hosts its own open Wi-Fi access point and serves a web page with the full event log. No router, no internet, no cloud — the ESP32 is the server.

Enabling it

When running the flash tool, answer y to the "Enable web log?" prompt. This compiles the Wi-Fi AP, DNS server, and web server into the firmware. Builds without this option are identical to previous versions — no extra power draw, no extra code.

Connecting

The ESP32 advertises a Wi-Fi network named {device-name}_{last 3 MAC octets} (e.g. Garage-Opener_A1B2C3). It is open — no password required. The app shows a Wi-Fi icon next to the paired device in Settings when the firmware supports this feature; tap it to trigger the system connection dialog pre-filled with the network name.

Once connected, any browser request is redirected to http://192.168.4.1 — the captive portal pops the log page automatically on most phones and laptops.

What the log shows

ColumnDescription
Date / TimeUTC timestamp sent by the phone at the moment of the open command
Result✓ Opened (successful auth) or ⚠ Auth fail (wrong PIN — useful for detecting probing)
ReasonManual tap, Geofence, or Voice
DevicePhone manufacturer and model that sent the command

The log holds the last 50 events in NVS flash — it survives reboots and deep sleep cycles. The page auto-refreshes every 30 seconds.

ℹ️

The ESP32 stays awake indefinitely while a device is connected to the AP. It returns to its normal sleep cycle once you disconnect.

Home Assistant integration

For wall-powered at-home deployments, the ESP32 can join your home WiFi and expose an HTTP webhook that any Home Assistant automation can call. BLE and the Android app continue to work in parallel — this is an additive feature, not a replacement.

Enabling it

When running the flash tool, answer y to the "Enable Home Assistant webhook?" prompt, then enter your WiFi SSID and password. These are compiled into the firmware and never saved to disk. The flash tool prints a ready-to-use rest_command snippet and curl command immediately after flashing.

Endpoints

MethodPathDescription
POST/openTriggers the relay. Requires Authorization: Bearer <pin> header.
GET/healthReturns {"status":"ok"}. No auth required. Use for HA availability checks.
GET/logFull event log page — same UI as the captive portal log, served over your LAN.

Home Assistant configuration

Add the following to configuration.yaml and reload HA:

rest_command:
  open_garage:
    url: "http://garage-opener.local/open"
    method: POST
    headers:
      Authorization: "Bearer <sha256-of-your-pin>"

Then call rest_command.open_garage from any automation action. The device is reachable via mDNS at http://<device-name>.local — no static IP or DHCP reservation needed.

ℹ️

Prefer mDNS (.local) unless you've reserved the ESP32's IP on your router. Without a DHCP reservation/static lease, a plain IP address can silently get reassigned to a different device after a lease renewal or router reboot, breaking or misdirecting the webhook — mDNS always follows the device, so it's the safer default. Once you've set a reservation, calling the ESP32 by IP instead (e.g. http://192.168.1.50/open) skips roughly 1–3 seconds of mDNS resolution on every call — same endpoints, same token, just faster.

curl test

curl -X POST http://garage-opener.local/open \
  -H "Authorization: Bearer <sha256-of-your-pin>"

The flash tool prints the exact hash to copy — you do not need to compute it manually.

Derive your token

If you need the hash again without reflashing, enter your PIN here — it never leaves your browser.

Bearer token (SHA-256)

Security

The Bearer token is SHA-256(PIN) as a lowercase hex string — not the raw PIN. This means a captured token cannot be used to authenticate over BLE, where the raw PIN is required. The token is still replayable on the HTTP endpoint itself (without TLS there is no way to prevent that), but the blast radius of a leak is contained to the LAN webhook only. The endpoint applies rate limiting: 3 failed auth attempts within 60 seconds returns 429 Too Many Requests for the remainder of that window.

The flash tool computes and prints the correct hash immediately after flashing — copy it directly into your configuration.yaml and curl commands.

ℹ️

This is the same security posture as ESPHome's HTTP/REST endpoints and most local HA integrations — unencrypted on the LAN, trusted-network model. The difference is that this integration keeps full BLE + Android Auto support, which ESPHome cannot provide.

ℹ️

Deep sleep is disabled in this mode. The device must be wall-powered. BLE advertising runs continuously so the Android app connects instantly whenever you are home.

Webhook mode (no ESP32 required)

Everything above describes this project's own ESP32 exposing a webhook. The Android app also supports the reverse: pairing directly with any webhook URL instead of an ESP32 at all. If your garage is already automated through Home Assistant, ESPHome, or any other system that can accept an HTTP request, you don't need this project's hardware — just point the app at that URL.

ℹ️

This is a separate, app-side feature from the firmware integration above. Pairing is mutually exclusive — a device is paired with either a BLE ESP32 or a webhook, never both at once.

ℹ️

At-home deployments (wall-powered, on your home WiFi) get the most out of combining both integrations: keep this project's ESP32 with its own Home Assistant firmware webhook enabled for full local RF range to the fob and reliable delivery via HA's automation logs, then trigger it from an HA automation. This is different from the shared/communal garage case this project primarily targets, where there is usually no WiFi or internet at the garage at all — BLE-direct pairing is the only option there, and app-side webhook mode doesn't apply.

Setting it up

On first launch, choose "I already have a webhook / Home Assistant automation" instead of scanning for a device. You can also switch to webhook mode later from Settings. Enter a name, the webhook URL, and — only if your endpoint requires it — a Bearer token under Advanced.

Authentication is optional

Home Assistant's native webhook trigger (Settings → Automations & Scenes → Webhook) needs nothing but the URL — the webhook_id embedded in it is itself the secret, so there's no separate header to configure. Point the app at that URL and you're done:

curl -X POST -H "Content-Type: application/json" \
  -d '{"reason":"manual","timestamp":1735689600,"model":"Pixel 8"}' \
  http://your-ha-ip:8123/api/webhook/your-webhook-id

If your target instead expects an Authorization: Bearer <token> header — for example, this project's own firmware HA integration described above — fill in the token field under Advanced. It's only sent when non-empty.

What gets sent

Every open request POSTs a small JSON body so the receiving automation can log or branch on it if you want:

{"reason": "geofence", "timestamp": 1735689600, "model": "Pixel 8"}

reason is one of manual, geofence, voice, or watch — the same trigger vocabulary used everywhere else in the app.

What still works

Every trigger source works identically regardless of which transport is active: manual tap, Android Auto, the Wear OS tile, geofence auto-open, and voice all call the same "open" action under the hood — only the transport underneath (BLE vs. HTTP) changes. Geofence auto-open in webhook mode skips the Android-Auto-connected gate (there's no ESP32/AA BLE state to check) and relies on the speed-based trigger path instead. Retry behavior mirrors BLE: 3 attempts with backoff, and an auth failure (HTTP 401/403) does not retry.

ℹ️

The app cannot verify or secure a third-party endpoint — that's the operator's responsibility. HTTPS is strongly recommended if the webhook is reachable outside your LAN.

Security model

Authentication flow

  1. Phone connects over BLE and reads the Nonce characteristic — 16 random bytes generated fresh on the ESP32 for this connection
  2. Phone computes HMAC-SHA256(password, nonce) and writes the 32-byte result to the Command characteristic
  3. ESP32 computes the same HMAC locally and compares. On match it triggers the relay (or transistor), writes 0x01 to Status. On mismatch it writes 0x00
  4. Nonce is discarded — the next connection generates a new one

Replay attack resistance

A captured BLE packet is useless: the nonce changes every connection. An attacker who records a valid HMAC cannot replay it because the ESP32 will generate a different nonce next time.

What never leaves the phone

Your password is stored only on the phone (in Android's EncryptedSharedPreferences) and in the ESP32's firmware. It is never transmitted over BLE or the internet, at any point.

🔒

The BLE transport itself is not encrypted (standard BLE advertising is unencrypted), but because the credential is an HMAC rather than the password itself, a full packet capture yields nothing useful to an attacker.

Troubleshooting

SymptomLikely causeFix
Serial monitor shows nothing Wrong baud rate or port Set 115200 baud; check COM port in Device Manager
Relay never clicks Wrong TRIGGER_MODE — try MODE_RELAY_HIGH, then MODE_RELAY Flash with correct mode for your hardware
Relay clicks but gate doesn't open Pulse too short or wrong contacts Increase RELAY_PULSE_MS in the flash tool; confirm wires are on COM and NO (not NC)
nRF Connect status always 00 Password mismatch Verify password in app exactly matches firmware
App not in Android Auto launcher Unknown sources not enabled (sideload only) Android Auto → tap version 10 times → enable Unknown sources
BLE scan finds nothing ESP32 not advertising or too far Check power; check serial output; move phone within 5 m
Scan times out immediately BLE permission denied Settings → Apps → Garage Opener → Permissions → allow Nearby devices
UI stuck on Sending… ESP32 in deep sleep during connect window The app retries 3× automatically. If it persists, check the ESP32 is advertising (serial monitor)
Gradle sync fails Android SDK not installed Android Studio → SDK Manager → install Android 15 (API 35)
